# Shelfwise Setup Reference

## Jenkins project type

Shelfwise uses a **Jenkins Pipeline project**.

The project is not created manually from the Jenkins UI. Jenkins Configuration
as Code loads `jenkins/jenkins.yaml`, and its Job DSL creates a pipeline job
named `shelfwise-bookstore`. The job checks out the `main` branch and reads the
pipeline definition from the root `Jenkinsfile`.

This is specifically a **Pipeline from SCM** setup:

- **SCM:** Git
- **Repository:** `GITHUB_REPOSITORY_URL`
- **Branch:** `main`
- **Pipeline file:** `Jenkinsfile`

It is not a Freestyle project or a Multibranch Pipeline.

## Vite

Vite is the frontend development server and production build tool.

Configuration:

```text
frontend/vite.config.js
```

Start the development application:

```bash
npm run dev
```

The frontend runs at:

```text
http://localhost:5173
```

Vite forwards `/api` requests to the local backend on port `3002`.

Create the production build:

```bash
npm run build
```

Generated files are written to:

```text
frontend/dist/
```

## Node.js and Express

Node.js runs the backend. Express defines the HTTP API.

Main files:

```text
backend/src/server.js
backend/src/app.js
backend/src/books.js
backend/src/metrics.js
```

Important endpoints:

| Endpoint | Purpose |
|---|---|
| `GET /health` | Health check |
| `GET /api/books` | Return the book catalog |
| `PATCH /api/books/:id/stock` | Change a book's stock |
| `GET /metrics` | Export Prometheus metrics |

The catalog is stored in memory. Restarting the backend resets stock to its
initial values.

## Nginx

The production frontend image uses Nginx.

Configuration:

```text

```

Nginx:

- Serves the files generated by Vite
- Sends `/api/*` requests to the backend service
- Provides `/healthz` for health checks
- Returns `index.html` for frontend routes

## Git and GitHub

Git tracks project versions. GitHub hosts the remote repository:

```text
https://github.com/Vampire-js/shelwise
```

Typical workflow:

```bash
git add .
git commit -m "Describe the change"
git push origin main
```

Jenkins checks out the GitHub repository when a build starts.

### Automatic-build status

Automatic builds on GitHub push are **not currently active**.

The Jenkins job contains a GitHub push trigger, but GitHub cannot reach a
Jenkins server at `localhost:8081`. Real automatic builds require:

1. A public HTTPS URL for Jenkins.
2. A GitHub webhook pointing to:

   ```text
   https://public-jenkins-url/github-webhook/
   ```

3. The webhook configured for push events.

## Jenkins

Jenkins runs in a separate Compose project named `shelfwise-jenkins`.

Files:

```text
jenkins-compose.yml
jenkins/Dockerfile
jenkins/jenkins.yaml
jenkins/plugins.txt
Jenkinsfile
```

### Jenkins container

`jenkins/Dockerfile` installs:

- Jenkins
- Git support
- Node.js
- Docker CLI
- Required Jenkins plugins

The host Docker socket is mounted into the Jenkins container:

```text
/var/run/docker.sock
```

This allows the pipeline to build Docker images using the host Docker daemon.

### Jenkins Configuration as Code

`jenkins/jenkins.yaml` configures:

- Local admin user
- Authorization
- Jenkins URL
- Pipeline job
- GitHub repository
- `main` branch
- GitHub push trigger

### Jenkins plugins

`jenkins/plugins.txt` installs plugins for:

- Configuration as Code
- Git and GitHub
- Pipeline execution
- Job DSL
- Docker workflow
- Pipeline stage view
- Timestamps
- JUnit test reports

### Jenkins pipeline

`Jenkinsfile` contains these stages:

1. **Checkout** — downloads the repository.
2. **Install** — runs `npm ci`.
3. **Test** — runs backend and frontend tests.
4. **Build** — creates the Vite production build.
5. **Package artifacts** — archives frontend, backend, and Kubernetes files.
6. **Build Docker images** — builds and exports application images.
7. **Post actions** — archives artifacts, fingerprints them, and cleans the
   workspace.

Start Jenkins:

```bash
export GITHUB_REPOSITORY_URL=https://github.com/Vampire-js/shelwise.git
export DOCKER_GID=$(stat -c '%g' /var/run/docker.sock)
docker compose -f jenkins-compose.yml up -d --build
```

Open:

```text
http://localhost:8081
```

## Kubernetes

Kubernetes runs containers as pods and maintains their desired state.

Files:

```text
k8s/namespace.yaml
k8s/backend.yaml
k8s/frontend.yaml
k8s/prometheus.yaml
k8s/grafana.yaml
k8s/kustomization.yaml
```

The resources use the `shelfwise` namespace.

### Backend deployment

The backend deployment uses:

- One replica
- Health and readiness probes
- CPU and memory requests
- CPU and memory limits
- Internal ClusterIP service

### Frontend deployment

The frontend deployment uses:

- Two replicas
- Health and readiness probes
- Resource requests and limits
- NodePort service on port `30088`

The two replicas allow the application to keep serving traffic while one
frontend pod is replaced.

### Kustomize

`k8s/kustomization.yaml` groups all Kubernetes resources.

Deploy everything:

```bash
kubectl apply -k k8s
```

Inspect:

```bash
kubectl get all -n shelfwise
```

## Minikube

Minikube creates the local Kubernetes cluster. It uses Docker as its driver.

Minikube and `kubectl` have different roles:

- **Minikube** creates and manages the cluster.
- **kubectl** sends commands to that cluster.

Deployment helper:

```text
scripts/minikube-deploy.sh
```

The script:

1. Starts Minikube.
2. Builds application images.
3. Loads the images into Minikube.
4. Applies the Kubernetes manifests.
5. Waits for deployments to become ready.

Run:

```bash
MINIKUBE_BIN="$HOME/.local/bin/minikube" ./scripts/minikube-deploy.sh
```

Useful commands:

```bash
minikube status
minikube ip
kubectl get pods -n shelfwise
kubectl get services -n shelfwise
```

## Kubernetes self-healing

The Deployment specifies the number of replicas that must exist. If a pod is
deleted or crashes, Kubernetes creates a replacement.

Demonstration:

```bash
./scripts/demonstrate-recovery.sh frontend
```

Manual demonstration:

```bash
kubectl get pods -n shelfwise -l app=frontend -w
```

In another terminal:

```bash
kubectl delete pod -n shelfwise \
  $(kubectl get pods -n shelfwise -l app=frontend \
  -o jsonpath='{.items[0].metadata.name}')
```

Kubernetes creates a new frontend pod to return to two replicas.

## Prometheus

Prometheus collects metrics from the backend every five seconds.

Docker configuration:

```text
monitoring/prometheus.yml
```

Kubernetes configuration:

```text
k8s/prometheus.yaml
```

Prometheus scrapes:

```text
http://backend:3000/metrics
```

Important metrics:

| Metric | Purpose |
|---|---|
| `bookstore_http_requests_total` | Number of HTTP requests |
| `bookstore_http_response_bytes_total` | Response traffic |
| `bookstore_http_request_duration_seconds` | Request duration |
| `bookstore_book_stock` | Remaining stock for each book |
| `bookstore_process_*` | Node.js process metrics |

Open:

```text
http://localhost:9090
```

## Grafana

Grafana reads Prometheus data and displays it as graphs.

Files:

```text
monitoring/grafana/provisioning/
monitoring/grafana/dashboards/bookstore-overview.json
```

Provisioning automatically creates:

- Prometheus datasource
- Shelfwise Bookstore dashboard

Dashboard panels include:

- HTTP request rate
- Response traffic
- Request latency
- Remaining stock per book

Open:

```text
http://localhost:3001
```

Default local credentials are `admin` / `admin` unless changed in `.env`.
